# نقشه‌راه هوش‌مصنوعی‌سازی پلتفرم مشاوره تحصیلی SDFR

> **به‌روزرسانی (پس از بازخورد کاربر):** نظر شما «حذف کامل مشاور» است، نه «ابزار کمکی برای مشاور» — و محور اصلی Agent باید خودِ «برنامه‌دادن» باشد (نه توضیحِ برنامه‌ای که یک الگوریتم ثابت تولید کرده). این دو گزینه واقعاً خیلی متفاوت‌اند و بخش ۱۰ (اضافه‌شده در پایین) دقیقاً همین را با جزئیات فنی باز کرده: چطور Agent می‌تواند خودش تصمیم‌گیرنده‌ی برنامه باشد، نه فقط مفسّر یک قانون ثابت.

## خلاصه مدیریتی

جواب کوتاه: **بله شدنی است، اما نه به شکلی که احتمالاً در ذهن دارید.** تصور رایج این است که یک "Agent" بزرگ می‌سازید که جای مشاور انسانی می‌نشیند و همه‌چیز را خودش انجام می‌دهد. نسخه واقعی و قابل‌اجرا این است: **بخش زیادی از چیزی که توضیح دادید اصلاً هوش‌مصنوعی نیست** (یادآوری‌ها، چک کردن ارسال گزارش، آنلاین بودن) و با همان Laravel Scheduler/Queue که الان دارید قابل‌ساخت است؛ فقط لایه نازکی از استدلال زبانی (LLM) روی چند نقطه‌ی مشخص (تفسیر آزمون شناخت دانش‌آموز، تحلیل روند مطالعه، تحلیل آزمون، و چت همیار عاطفی) اضافه می‌شود. این تفکیک، هم هزینه را واقعی و قابل کنترل می‌کند و هم ریسک را.

نکته درباره اسکیل‌هایی که اشاره کردید: از میان پنج مورد، `engineering:system-design` را برای طراحی معماری به‌کار گرفتم. `product-tracking-model-product`، `productivity:start`، `marketing:performance-report` و `finance:financial-statements` برای این سؤال مناسب نبودند (به ترتیب برای طراحی رویدادهای آنالیتیکس، مدیریت تسک شخصی، گزارش عملکرد کمپین بازاریابی، و صورت‌های مالی استاندارد GAAP ساخته شده‌اند) — به‌جایشان یک تحلیل هزینه/فایده عملی و مستقیم برای همین تصمیم آورده‌ام.

این سند بر اساس بررسی واقعی ریپوی شما (`sdfr-laravel`) نوشته شده: پروژه‌ای بالغ با **۳۶۵ کامپوننت Livewire، ۱۷۰ مدل، و ۱۸ سرویس** — یعنی منطق کسب‌وکار زیادی از قبل نوشته و تست‌شده است (مثلاً `AssessmentScoringService`، `TrialWeekService`، `ExamPlanningService`، `DailyReport`/`DailyReportDetail`). این یک نکته حیاتی است: **بازنویسی کامل، منطقی نیست.** مسیر درست، افزودن یک لایه Agent روی همین سیستم است، نه دور انداختنش.

## ۱. آیا واقعاً شدنی است؟

فنی: کاملاً. از نظر داده هم وضعیت شما خیلی بهتر از اکثر پروژه‌هایی است که می‌خواهند Agent بسازند، چون داده‌هایتان **ساخت‌یافته (structured)** است نه انبوه سند بدون‌ساختار. این یعنی برخلاف تصور رایج، به RAG سنگین (جست‌وجوی برداری روی اسناد) نیاز چندانی ندارید؛ چیزی که نیاز دارید یک **Agent با ابزار (Tool-calling) روی دیتابیس خودتان** است: Agent به جای «جست‌وجو در اسناد»، از طریق API به `DailyReport`، `Assessment`، `AdvisingSession` و... کوئری می‌زند و خروجی را به زبان طبیعی تبدیل می‌کند.

آنچه سخت‌تر از تصور اولیه است:
- **تشخیص تقلب واقعی** با تحلیل متنی LLM قابل‌اتکا نیست. برای تقلب در آزمون (نه فقط ناهنجاری زمانی) به ابزارهای دیگر (قفل مرورگر، پراکتورینگ وب‌کم) نیاز است که خارج از حوزه Agent زبانی است. LLM فقط می‌تواند **الگوهای مشکوک** (مثلاً زمان پاسخ غیرعادی کوتاه، شباهت متن پاسخ به بانک سؤال) را پرچم بزند، نه اثبات تقلب.
- **همیار عاطفی** حساس‌ترین بخش پروژه است، نه به‌خاطر فناوری بلکه به‌خاطر مسئولیت: کاربران شما دانش‌آموز هستند (احتمالاً برخی زیر ۱۸ سال)، و یک ایجنت که خودش را «همراه روزهای سخت» معرفی می‌کند وارد حوزه‌ای می‌شود که مرز آن با حمایت روانی واقعی باریک است. این بخش را در قسمت ریسک‌ها مفصل باز کرده‌ام.

## ۲. یک تصحیح مهم در مدل ذهنی: Workflow در برابر Agent

خودتان درست حدس زدید: «قاعدتا Workflow فکر نمی‌کنم باشه، البته هستش یجوری». دقیقاً همین‌طور است. سیستم شما را باید سه لایه ببینید، نه یک Agent یکپارچه:

**لایه ۱ — اتوماسیون قطعی (Deterministic، بدون AI):**
زمان‌بندی، یادآوری پیامکی نبود گزارش، چک آخرین‌بار آنلاین‌بودن، اجرای `TrialWeekService`/`ExamPlanningService` برای تولید برنامه. اینها همین امروز با Laravel Scheduler + Queue (که در پروژه‌تان هست) قابل ساخت است. **هیچ توکن LLM‌ای اینجا مصرف نمی‌شود** و هزینه‌اش عملاً صفر است.

**لایه ۲ — استدلال و تفسیر (LLM به‌صورت Batch/Async):**
تفسیر نتیجه آزمون طبقه‌بندی، تولید بینش هفتگی از روی الگوی مطالعه (`DailyReport`)، تحلیل تشخیصی آزمون (`EssayExamQuestionScore`). این‌ها کارهایی هستند که یک Job در صف اجرا می‌کند، یک یا چند بار در روز/هفته، خروجی‌اش را در دیتابیس ذخیره و در همان پنل Livewire موجود نمایش می‌دهد. **نه real-time است، نه نیاز به چت دارد.**

**لایه ۳ — تعامل مکالمه‌ای (Agent واقعی، real-time):**
فقط همیار عاطفی و شاید توضیح برنامه به زبان طبیعی («چرا امروز این پارت رو بهم دادی؟»). این تنها بخشی است که واقعاً به معنای متعارف کلمه «Agent چت‌محور» است و باید جدا از بقیه طراحی و کنترل شود.

این تفکیک مستقیماً روی هزینه و پیچیدگی مهندسی اثر می‌گذارد: اکثر آنچه توصیف کردید در لایه ۱ و ۲ است، نه لایه ۳.

## ۳. معماری پیشنهادی

```
┌─────────────────────┐        ┌──────────────────────────┐
│   Next.js (React)   │◄──────►│   Laravel API (Sanctum)  │
│  چت همیار + داشبورد  │  REST  │  همان app/Models,        │
│  دانش‌آموز جدید       │        │  Services موجود شما      │
└─────────────────────┘        │  + Resource Controllers   │
                                │  جدید روی سرویس‌های فعلی   │
        ▲                      └──────────┬────────────────┘
        │                                 │
        │ WebSocket/Polling               │ Job Dispatch
        │ (وضعیت آنلاین، پیام‌ها)          ▼
┌───────┴──────────┐          ┌───────────────────────────┐
│  Laravel Reverb   │          │   Laravel Queue Worker    │
│  یا Pusher برای    │          │   (Scheduler + Jobs)      │
│  حضور/پیام لحظه‌ای │          │   نوشتن یادآوری، تحلیل     │
└────────────────────┘          │   هفتگی، تفسیر آزمون      │
                                 └──────────┬────────────────┘
                                            │ HTTPS
                                            ▼
                                 ┌───────────────────────────┐
                                 │  Agent/LLM Gateway         │
                                 │  (AvalAI / Metis یا مشابه  │
                                 │  به‌خاطر تحریم) →           │
                                 │  OpenAI/Claude/Gemini/     │
                                 │  DeepSeek                  │
                                 └───────────────────────────┘
```

### نکات کلیدی معماری

- **Laravel همان سیستم مرجع (source of truth) باقی می‌ماند.** ۱۷۰ مدل و ۱۸ سرویس شما دور ریخته نمی‌شود؛ فقط یک لایه Resource/API روی همان سرویس‌ها (`TrialWeekService`, `AssessmentScoringService`, ...) اضافه می‌کنید تا هم Livewire فعلی و هم Next.js جدید بتوانند از آن استفاده کنند.
- **پنل ادمین/مشاور را فعلاً به Next.js نبرید.** Livewire برایش کاملاً کافی و پربازده است؛ Next.js را فقط برای تجربه‌ی جدید و AI-محور دانش‌آموز (چت، داشبورد شخصی‌سازی‌شده) به‌کار ببرید. مهاجرت کامل فرانت به Next.js یک پروژه‌ی جدا و پرهزینه است — آن را با پروژه‌ی Agent قاطی نکنید.
- **مدل `Conversation`/`ConversationMessage` که همین الان در پروژه‌تان هست را برای تاریخچه‌ی چت همیار عاطفی گسترش دهید**، به‌جای ساخت جدول جدید از صفر.
- **RAG واقعی لازم نیست.** به‌جایش «context injection ساخت‌یافته»: قبل از هر فراخوانی LLM، یک خلاصه‌ی فشرده و عددی از وضعیت دانش‌آموز (نوع دانش‌آموز، ساعات مطالعه هفته اخیر، نمرات آزمون اخیر) به‌صورت JSON در پرامپت قرار می‌گیرد — نه کل تاریخچه خام.
- **Model Routing**: برای کارهای ارزان و پرحجم (خلاصه‌سازی، طبقه‌بندی ساده) از مدل ارزان (مثل GPT-5.6 Luna یا Gemini Flash) و برای کارهای حساس (تفسیر روان‌سنجی، چت همیار) از مدل قوی‌تر (Sonnet/Opus) استفاده کنید. این تفکیک شاید ۵ تا ۱۰ برابر در هزینه صرفه‌جویی کند.
- **دروازه‌ی دسترسی به API به‌خاطر تحریم**: OpenAI و Anthropic صریحاً دسترسی مستقیم از IP/حساب ایران را مسدود می‌کنند. مسیر رایج و فعال در حال حاضر استفاده از دروازه‌های داخلی مثل **AvalAI** یا **Metis AI** است که API سازگار با OpenAI/Anthropic ارائه می‌دهند و صورتحساب ریالی دارند ([مستندات AvalAI](https://docs.avalai.ir/en/quickstart)). این یک وابستگی حیاتی است — قبل از شروع، سیاست حریم خصوصی و پایداری سرویس این واسط‌ها را بررسی کنید، چون داده‌ی دانش‌آموزان از آن عبور می‌کند.

## ۴. نگاشت دقیق سناریوهای شما به معماری

| سناریوی شما | لایه | پیاده‌سازی |
|---|---|---|
| آزمون بدهد، Agent بشناسدش | ۲ (Batch) | ارتقای `AssessmentInterpretationService`: خروجی امتیاز فعلی + یک فراخوانی LLM که تفسیر زبان‌طبیعی + برچسب نوع دانش‌آموز تولید می‌کند |
| برنامه بدهد | ۱ (قطعی) | همان `TrialWeekService`/`ExamPlanningService` فعلی؛ Agent فقط توضیح متنی برنامه را تولید می‌کند، نه خودِ زمان‌بندی را |
| ثبت ساعت مطالعه و فهمیدن ساعت شروع | ۱ (قطعی) | از `DailyReportDetail` موجود، Query ساده روی timestamp؛ نیازی به LLM نیست مگر برای خلاصه‌ی هفتگی زبانی |
| یادآوری نبود گزارش شب | ۱ (قطعی) | Laravel Scheduler هر شب چک می‌کند، از کانال SMS موجود (`SendStudentPlanSms` و مشابه) استفاده می‌کند — صفر هزینه‌ی LLM |
| چه ساعتی آنلاینه | ۱ (قطعی) | `last_seen_at` + heartbeat ساده، بدون AI |
| تقلب دارد می‌کند یا نه | ۲ (با احتیاط) | فقط پرچم‌گذاری ناهنجاری آماری (نه اثبات)؛ برای قطعیت به ابزار پراکتورینگ جدا نیاز دارید |
| تحلیل آزمون‌ها | ۲ (Batch) | Job هفتگی/پس از هر آزمون روی `EssayExamQuestionScore` |
| همیار عاطفی | ۳ (Real-time، پرریسک) | چت با Guardrail، تشخیص کلمات بحرانی، ارجاع به انسان |

## ۵. تحلیل هزینه

قیمت‌های تقریبی به ازای هر میلیون توکن (شهریور ۱۴۰۵ / سپتامبر ۲۰۲۶، از منابع فعلی بازار):

| مدل | ورودی | خروجی | مصرف پیشنهادی |
|---|---|---|---|
| GPT-5.6 Luna | $0.20 | $1.20 | خلاصه‌سازی، طبقه‌بندی ارزان |
| Gemini 2.5 Flash | $0.25 | $1.50 | کارهای پرحجم و کم‌ریسک |
| DeepSeek V3.2 | $0.28 | $0.42 | جایگزین ارزان با کیفیت قابل‌قبول |
| Claude Sonnet 5 | $2.00 | $10.00 | تفسیر روان‌سنجی، تحلیل آزمون، چت همیار |
| Claude Opus 5 | $5.00 | $25.00 | فقط موارد حساس/پیچیده |

برآورد سرانگشتی (نه قیمت قطعی) برای هر دانش‌آموز فعال در ماه، با فرض استفاده از Sonnet برای کارهای حساس:
- تفسیر آزمون طبقه‌بندی (یک‌بار در فصل، مستهلک ماهانه): ناچیز
- تحلیل هفتگی روند مطالعه (۴ بار در ماه، هر بار حدود ۲هزار توکن ورودی/۸۰۰ خروجی): حدود ۵ سنت
- تحلیل آزمون (۲ بار در ماه): حدود ۲ سنت
- چت همیار عاطفی (فرض ۱۵ پیام در ماه): حدود ۶ سنت

**جمع تقریبی: کمتر از ۲۰ سنت (کمتر از یک دلار) به ازای هر دانش‌آموز فعال در ماه** برای هزینه‌ی خام API — رقمی که در مقیاس چند صد یا چند هزار دانش‌آموز، در مقابل حقوق مشاوران انسانی که فعلاً این کار را انجام می‌دهند، بسیار کوچک است. **اما دو نکته مهم:**

1. این فقط هزینه‌ی API خام است. کارمزد دروازه‌ی داخلی (AvalAI/Metis)، زیرساخت Queue/Worker اضافه، و از همه مهم‌تر **هزینه‌ی توسعه و نگهداری** (که یک‌بار نیست، مداوم است — پرامپت‌ها باید نسخه‌بندی و ارزیابی شوند) را باید جدا حساب کنید.
2. کاهش هزینه واقعی است **فقط در مقیاس**. اگر تعداد دانش‌آموزان کم است، هزینه‌ی ساخت و نگهداری این زیرساخت ممکن است از هزینه‌ی همان چند مشاور انسانی بیشتر شود. این یک سرمایه‌گذاری با بازگشت در مقیاس بالاست، نه صرفه‌جویی فوری روز اول.

چارچوب درست‌تر برای فکر کردن به این پروژه: **«یک مشاور انسانی می‌تواند چند برابر دانش‌آموز بیشتر پوشش دهد»** (چون کارهای تکراری را Agent انجام می‌دهد)، نه «مشاور را کامل حذف می‌کنیم».

## ۶. دانش و مهارت‌های لازم برای ساخت این سیستم

خبر خوب: نیازی به یادگیری Machine Learning یا آموزش مدل نیست — همه‌چیز روی API مدل‌های آماده سوار می‌شود. مهارت‌های واقعی موردنیاز:

1. **طراحی Tool-calling**: تعریف یک مجموعه‌ی محدود و پایدار از "ابزار"هایی که Agent می‌تواند صدا بزند (مثلاً `get_student_summary`, `create_reminder`, `flag_for_advisor`) — نه دادن دسترسی خام به کل دیتابیس.
2. **مدیریت Context**: تصمیم اینکه در هر فراخوانی دقیقاً چه داده‌ای وارد پرامپت شود (خلاصه، نه خام).
3. **Structured Output**: اجبار خروجی LLM به فرمت JSON با اسکیمای مشخص (اکثر SDKها این را پشتیبانی می‌کنند) تا نتیجه قابل ذخیره در دیتابیس ساخت‌یافته‌ی فعلی‌تان باشد.
4. **Eval/تست پرامپت**: قبل از هر تغییر پرامپت، روی یک مجموعه نمونه (مثلاً ۳۰-۵۰ پروفایل دانش‌آموز واقعی) تست شود که خروجی خراب نشده — این جایگزین Unit Test برای بخش AI است.
5. **Observability**: لاگ‌کردن هر تصمیم Agent (ورودی، خروجی، هزینه، زمان) — برای یک پروژه‌ی آموزشی حساس به‌خصوص حیاتی است، هم برای دیباگ و هم برای پاسخ‌گویی احتمالی به والدین/نهادها.
6. **لایه ایمنی (Safety)**: فیلتر محتوای نامناسب، تشخیص کلمات کلیدی بحرانی (خودآزاری، افسردگی شدید) و مسیر ارجاع فوری به انسان — این بخش را نباید خودتان از صفر طراحی کنید؛ چارچوب‌های آماده (Guardrails/Moderation API ارائه‌دهندگان) را به‌کار ببرید.

این مهارت‌ها را می‌توانید در حد کافی برای یک MVP در چند هفته با مطالعه‌ی مستندات OpenAI/Anthropic Agent SDK و ساخت یک Agent محدود (مثلاً فقط تحلیل آزمون) یاد بگیرید — پیشنهاد می‌کنم دقیقاً از همین‌جا شروع کنید، نه از همیار عاطفی.

## ۷. ریسک‌ها و نکات احتیاط

- **همیار عاطفی = حوزه حساس مسئولیتی.** کاربران شما دانش‌آموز (احتمالاً برخی زیر سن قانونی) هستند. یک Agent که نقش «همراه روزهای سخت» بازی می‌کند، اگر با حرف‌های مربوط به اضطراب امتحان یا فشار روانی مواجه شود و پاسخ نامناسب بدهد، ریسک واقعی دارد. توصیه: این بخش را صریحاً محدود به «انگیزه‌بخشی و برنامه‌ریزی درسی» نگه دارید، از ادعای «حمایت روانی» خودداری کنید، و یک مسیر تشخیص/ارجاع به انسان (یا حداقل نمایش اطلاعات تماس حمایتی) برای پیام‌های پرخطر بسازید.
- **حریم خصوصی داده‌ی دانش‌آموز**: قبل از ارسال داده به هر LLM (چه مستقیم چه از طریق دروازه‌ی داخلی)، اسم واقعی و اطلاعات هویتی را با شناسه جایگزین کنید؛ فقط داده‌ی لازم برای همان کار خاص را بفرستید.
- **وابستگی به دروازه‌ی ثالث (AvalAI/Metis)**: این سرویس‌ها فعلاً پایدارند اما یک نقطه‌ی تک‌شکست و یک لایه‌ی اعتماد اضافه هستند. سیاست نگهداری داده‌شان را قبل از تعهد بررسی کنید.
- **توهم مدل (Hallucination) در تحلیل**: هسته‌ی زمان‌بندی و منطق برنامه باید همیشه قطعی (کد فعلی شما) بماند؛ LLM فقط توضیح/تحلیل تولید کند، نه تصمیم نهایی نمرات یا برنامه.
- **هزینه‌ی مصرف‌محور**: برخلاف حقوق ثابت مشاور، هزینه‌ی API با رشد مصرف رشد می‌کند و می‌تواند غافلگیرکننده باشد — از روز اول محدودیت مصرف (rate limit / budget cap) بگذارید.
- **بازنویسی هم‌زمان فرانت (Next.js) و Agent، ریسک را دوچندان می‌کند.** این دو را جدا اجرا کنید.

## ۸. مسیر پیاده‌سازی مرحله‌ای پیشنهادی

1. **فاز صفر**: Livewire/معماری فعلی دست‌نخورده می‌ماند. فقط چند Resource Controller روی سرویس‌های موجود اضافه می‌کنید.
2. **فاز ۱ (کم‌ریسک، اعتبارسنجی pipeline)**: یک Job در صف که پس از هر آزمون، `EssayExamQuestionScore` را می‌خواند و یک تحلیل تشخیصی متنی تولید و در همان پنل Livewire فعلی نمایش می‌دهد. هیچ چت، هیچ Next.js لازم نیست. این فاز کل زنجیره (استخراج داده → پرامپت → خروجی ساخت‌یافته → ذخیره) را با کمترین ریسک تست می‌کند.
3. **فاز ۲ (اتوماسیون بدون AI، ارزش بالا)**: یادآوری‌های شبانه‌ی نبود گزارش و چک آنلاین‌بودن — تقریباً بدون هزینه‌ی LLM، روی همان کانال‌های SMS موجودتان.
4. **فاز ۳ (تفسیر دانش‌آموز)**: ارتقای `AssessmentInterpretationService` با لایه‌ی LLM.
5. **فاز ۴ (همیار عاطفی، Beta محدود)**: فقط بعد از این‌که فازهای ۱ تا ۳ جواب داد، با یک گروه کوچک آزمایشی، Guardrail کامل، و احتمالاً همین‌جا اولین باری که واقعاً Next.js لازم می‌شود (تجربه‌ی چت).
6. **فاز ۵**: تصمیم‌گیری درباره‌ی گسترش فرانت به Next.js برای کل تجربه‌ی دانش‌آموز، بر اساس داده‌ی واقعی فازهای قبل، نه حدس اولیه.

## ۹. جمع‌بندی

این پروژه شدنی است و پایه‌ی داده‌ای‌تان (۱۷۰ مدل ساخت‌یافته) برای آن آماده‌تر از اکثر پروژه‌های مشابه است. هزینه‌ی خام API به ازای هر دانش‌آموز واقعاً پایین است و در مقیاس، صرفه‌جویی واقعی ایجاد می‌کند — اما به‌شرط شروع از کوچک‌ترین و کم‌ریسک‌ترین بخش (تحلیل آزمون/گزارش)، نه از بزرگ‌ترین و حساس‌ترین بخش (همیار عاطفی که جایگزین کامل مشاور می‌شود). چارچوب ذهنی درست: مشاور انسانی حذف نمی‌شود، بلکه ظرفیتش چند برابر می‌شود چون کارهای تکراری را Agent برمی‌دارد.

## ۱۰. حذف کامل مشاور در برابر ابزار کمکی — و طراحی دقیق «هسته‌ی برنامه‌ریز»

### ۱۰.۱ جواب صادقانه به سؤال «کدام درست است؟»

این سؤال، سؤال کسب‌وکاری شماست و تصمیمش با شماست؛ اما از نظر فنی/ریسک باید صریح باشم: **بین «حذف مشاور» و «آزمایش قبل از حذف مشاور» تفاوت است، نه بین «حذف» و «نگه‌داشتن مشاور برای همیشه».** پیشنهاد قبلی من («ابزار برای مشاور») را کنار می‌گذارم چون شما هدف را روشن کردید. اما یک نکته‌ی مهندسی، نه یک بازگشت به همان حرف: **قبل از اینکه Agent بدون هیچ نظارتی برای همه‌ی دانش‌آموزان برنامه بدهد، باید در یک بازه‌ی محدود (مثلاً روی چند صد دانش‌آموز واقعی) خروجی‌اش را با آنچه یک مشاور خوب می‌داد مقایسه کنید.** این «shadow validation» است، نه «مشاور به‌عنوان ویژگی دائمی محصول» — دقیقاً مثل تست A/B قبل از انتشار کامل یک فیچر. بعد از اینکه اعتماد ایجاد شد، مشاور کاملاً از مسیر برنامه‌دهی خارج می‌شود. اگر این مرحله‌ی اعتبارسنجی را حذف کنید، ریسک این است که اولین باری که Agent به یک دانش‌آموز نزدیک کنکور برنامه‌ی غلط بدهد، همان دانش‌آموز واقعی است که ضرر می‌کند — نه یک تست.

### ۱۰.۲ چرا هسته‌ی برنامه‌ریز، «سخت‌ترین بخش» است — و چطور واقعاً ساخته می‌شود

حرف شما درست است: این بخش محور همه‌چیز است. اما یک نکته‌ی فنی حیاتی وجود دارد که باید روشن باشد: **اگر منظورتان این است که یک LLM مستقیماً و آزادانه یک برنامه‌ی ماهانه/روزانه را از صفر به‌صورت متن یا JSON تولید کند، این روش در عمل شکننده و غیرقابل‌اعتماد می‌شود** — LLMها در محاسبات دقیق (جمع ساعت‌ها، پوشش کامل سرفصل، رعایت هم‌زمان چند قید مثل «زمان باقیمانده + ضریب درس + زمان آزاد دانش‌آموز») ضعیف عمل می‌کنند و نتیجه می‌تواند بین دو اجرا برای یک دانش‌آموز یکسان، متفاوت باشد یا برخی مباحث را کلاً جا بیندازد — چیزی که برای آماده‌سازی کنکور غیرقابل‌قبول است.

راه‌حلی که واقعاً در سیستم‌های Agent تولیدی به‌کار می‌رود (نه یک مصالحه، بلکه همان الگوی استاندارد مهندسی Agent) این است: **Agent را از یک موتور محاسباتی جدا کنید و Agent را تصمیم‌گیرنده‌ی استراتژی + تحلیل‌گر بگذارید، نه خودِ ماشین‌حساب.** دقیقاً همان‌طور که یک Agent خوب برای جمع دو عدد به‌جای حدس‌زدن، از ابزار Calculator استفاده می‌کند، اینجا هم Agent باید از یک «موتور تخصیص» به‌عنوان ابزار (Tool) استفاده کند. دو تکه:

**تکه‌ی اول — موتور تحلیل و وضعیت دانش‌آموز (Student State Engine، «تحلیل دائمی» که خودتان گفتید):**
این بخش پیوسته (روزانه، بعد از هر گزارش/آزمون جدید) اجرا می‌شود و از داده‌های واقعی موجود در پروژه‌ی شما تغذیه می‌کند:
- **امتیاز تسلط به‌ازای هر مبحث/فصل** — از روی نتایج `EssayExamQuestionScore` و `Assessment`، به تفکیک `CcSubject`/`CcChapter`/`CcTopic`
- **روند (Trend)** — آیا در این مبحث پیشرفت می‌کند یا افت کرده (مقایسه‌ی چند آزمون اخیر، نه یک عدد ایستا)
- **پیوستگی مطالعه (Momentum)** — از الگوی `DailyReport`/`DailyReportDetail`: منظم مطالعه می‌کند یا نه، چند روز از آخرین مطالعه‌ی یک مبحث خاص گذشته (افت حافظه/فراموشی، شبیه منطق مرور فاصله‌دار)
- **زمان باقیمانده** — دقیقاً همان چیزی که گفتید؛ خبر خوب این است که مدل‌های `ExamCountdownSetting`/`KonkurCountdownSetting` از قبل در پروژه‌ی شما وجود دارند و همین الان روزشمار را نگه می‌دارند — این بخش را عملاً از صفر نمی‌سازید
- **وزن/ضریب درس** برای رشته و هدف دانش‌آموز (اگر جدول ضرایب کنکور برای هر رشته ندارید، این یکی از معدود چیزهایی است که باید به‌عنوان داده‌ی مرجع اضافه کنید)
- **زمان آزاد واقعی دانش‌آموز** — از `AdvisingPreSessionFreeTime` موجود

خروجی این موتور یک عدد یا برچسب خام نیست، یک **بردار ساخت‌یافته از اولویت‌ها** است: «فلان مبحث: ضعیف + رو به افت + ضریب بالا + زمان کم مانده = فوریت بسیار بالا»، «فلان مبحث: قوی + پایدار = فقط مرور دوره‌ای کم‌حجم لازم دارد». اینجاست که «تقویت ضعیف‌ها و مدیریت/پیشرفته‌کردن قوی‌ها» که گفتید عملاً اتفاق می‌افتد — نه با یک قانون سراسری، بلکه چون هر مبحث امتیاز اولویت جداگانه می‌گیرد.

**تکه‌ی دوم — موتور تخصیص/زمان‌بندی (Planner، ابزاری که Agent صدا می‌زند):**
یک الگوریتم تخصیص (شبیه یک مسئله‌ی بهینه‌سازی وزن‌دار/knapsack) که ورودی‌اش خروجی تکه‌ی اول + تقویم واقعی (تا امتحان بعدی چند روز، هر روز چند ساعت زمان آزاد) است، و خروجی‌اش تخصیص دقیق ساعت به هر مبحث در هر روز/هفته/ماه است. این بخش کاملاً قطعی، سریع (میلی‌ثانیه، نه چند ثانیه صدازدن LLM)، رایگان (بدون هزینه‌ی توکن)، و قابل‌ممیزی است — می‌توانید دقیقاً نشان دهید چرا فلان مبحث امروز در برنامه است.

**نقش Agent/LLM در این معماری** (که همان چیزی است که واقعاً «هوشمندی» و جای‌گزینی مشاور را می‌سازد):
1. تنظیم پویای وزن‌ها و استراتژی موتور تخصیص بر اساس تحلیل — مثلاً «۳ هفته مانده به کنکور، نسبت تخصیص را کاملاً به‌سمت مرور مباحث ضعیفِ پرضریب بچرخان و مبحث جدید حذف کن» — این یک تصمیم استراتژیک سطح‌بالاست، دقیقاً کاری که یک مشاور خوب در ذهنش انجام می‌دهد، و Agent با فراخوانی موتور تخصیص با پارامترهای متفاوت، عملاً همین تصمیم را می‌گیرد
2. تفسیر سیگنال‌های کیفی/متنی (مثلاً یادداشت آزاد دانش‌آموز در گزارش روزانه) و تبدیلش به ورودی عددی برای موتور تحلیل
3. توضیح برنامه به زبان طبیعی برای دانش‌آموز («چرا امروز حسابان به‌جای فیزیک؟»)
4. تشخیص موارد استثنا/غیرعادی که قوانین از پیش تعریف‌شده پوششش نمی‌دهند و پرچم‌گذاری برای بازبینی

نتیجه: **بله، Agent است که تصمیم می‌گیرد، نه یک الگوریتم ثابتِ تنظیم‌شده توسط مشاور** — چون خود Agent است که پارامترهای الگوریتم را پیوسته و بر اساس تحلیل زنده‌ی دانش‌آموز تعیین می‌کند. تفاوت با پیشنهاد اول من این است که آنجا فرض بر این بود مشاور همچنان تنظیمات را دستی انجام می‌دهد؛ اینجا خودِ تحلیل، جای تنظیم دستی مشاور را می‌گیرد. اما بخش «تولید دقیق برنامه» را از تولید متن آزاد LLM جدا نگه می‌داریم چون قابل‌اعتماد نیست — این تصمیم مهندسی است، نه محافظه‌کاری در برابر تصمیم شما.

### ۱۰.۳ پیامد روی نقشه راه

با این تصحیح، فاز ۱ پیشنهادی (بخش ۸) باید عوض شود: به‌جای شروع از تحلیل آزمون به‌تنهایی، **اول موتور تحلیل دانش‌آموز + موتور تخصیص را روی داده‌های واقعی گذشته‌ی چند ده دانش‌آموز بسازید و در حالت Shadow (بدون نمایش به دانش‌آموز) با برنامه‌ای که مشاور واقعی داده مقایسه کنید.** وقتی این تطابق قابل‌قبول شد، برنامه‌ی تولیدشده مستقیم به دانش‌آموز می‌رود و مشاور از مسیر خارج می‌شود — دقیقاً مطابق نظر شما.
